# DOCX 课程资料分片修复（离线）

## 定位结果

用户课程复习DOCX为1,774,248字节（约1732.7 KiB），不是依据文件大小推算文本。只读解析原始留存文件：旧解析26,475字符，1059个顶层段落，其中270个空段落，0个表格。按512字符、64重叠预计59片；原本机启动器硬限制32片，因而在分片检查阶段失败。没有发现重复分片、异常表格膨胀或无限循环。数据库失败记录为0片，没有Chunk行或FAISS残留。

该错误路径先于Embedding适配器调用，因此此次失败未调用Embedding，不是模型服务或费用问题。本轮修复与测试也没有真实模型请求。

## 策略变化

| 项目 | 原本机模式 | 新本机模式 |
| --- | --- | --- |
| 分片字符目标 | 512 | 640 |
| 重叠字符目标 | 64 | 80（均为12.5%） |
| 分片方式 | 固定字符窗口 | 优先段落换行边界，长段落有界回退 |
| 单片UTF-8上限 | 无显式切分上限 | 1984字节；兼容Guard的字节×4+256≤8192估算 |
| 单文档片数上限 | 32 | 128 |
| 解析字符上限 | 40000 | 120000 |
| 每批/总批数 | 每批8条，隐含最多4批 | 每批8条，最多16批；瞬时重试最多32次尝试 |
| 文件大小 | 2 MiB | 2 MiB不变；DOCX解压后50 MiB上限不变 |

不是无限扩大片数：字符、字节、总片数、批次、会话剩余尝试、累计预算都有限。首次模型请求前仍检查整文档的费用及每批一次重试余量，实际HTTP仍逐次原子预扣，不设单轮金额门槛。默认普通模式保留原分片行为，本机启动器显式启用新策略，现有索引不自动重建。

标题按Word Heading/标题层级保留结构，清除空段落、重复空行和零宽格式符；表格按实际单元格提取，跳过合并单元格重复引用，保留嵌套表格内容并限制嵌套8层。不会对全文相同句子全局去重，以免删掉不同章节的真实内容。

较长分片保留更多局部上下文，段落边界减少句子被截断；相同12.5%重叠保留跨片信息。代价是检索粒度略粗、Prompt可能更长，后续可独立做质量评测；本轮不付费评测。

## 原文件新统计

只读分析结果：26,137字符、49片，最大640字符/1796 UTF-8字节，正常需要7次Embedding请求。含每批一次受控瞬时重试最多14次尝试。

按既有参考原价和Guard输入余量，文档输入费用预留约¥0.159814，含重试风险预留约¥0.319628；不是实际费用、不是新的单轮费用限制，服务端usage及现有累计账本仍是最终核算依据。原文件只读校验未变。

**解析和分片已通过，不代表已经完成真实向量化。** 本轮未重新处理用户原文，原失败记录仍为failed。真实索引和模型兼容性需用户确认后执行这7次请求才能验证。

## 使用与重试

重启后端以加载新启动器配置，在backend目录执行（先在旧窗口Ctrl+C）：

```powershell
.\.venv\Scripts\python.exe tests/start_web_demo.py --enable-authorized-web-demo --enable-local-writes --session-name docx-fix-01
```

前端刷新127.0.0.1:5189。原失败资料无需删除：

1. 点击“分析原文件与重试”。GET processing-plan仅本地解析，展示文字量、片数、预计批次和风险预留，不调用模型、不更改文档状态。
2. 核对后点击“确认重试并生成索引”。POST retry必须携带确认头，仅允许failed记录，复用同一个文档ID和原始文件，不删除原文。
3. 成功才标记ready，失败则清理部分索引和Chunk、保留failed及诊断信息。不会静默重跑已就绪文件。

新上传在真实模式下也先本地分析；点击第二次“确认并生成索引”才处理入库。分析使用临时文件，不创建文档记录或向量。若超限，返回已解析字符数和实际片数；达到解析字符上限则报告“至少”多少字符并停止，不把部分提取当完整统计。
